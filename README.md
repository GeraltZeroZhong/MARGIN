# MARGIN

**Modality Attribution of Residual Gain in Inverse-Folding Networks**

MARGIN provides configurable tools for comparing sequence and structure model
scores at protein residue positions. It builds typed registries, samples sequence
states, constructs structure controls, measures score differences, and evaluates
how well frozen sequence features predict those differences.

The package includes a deterministic synthetic workflow for exercising the full
software pipeline on a CPU. Its geometry, sequences, scores, and assay labels are
generated by code. The resulting `SYNTHETIC_ONLY` decision describes software
validation; scientific interpretation requires independently collected evidence.

## Installation

Use Python 3.10 or later. From a source checkout:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
```

The core dependencies are NumPy, pandas, PyArrow, SciPy, scikit-learn, Biopython,
Matplotlib, Pydantic, and PyYAML. After these dependencies are installed, the
synthetic workflow runs locally without model downloads.

## Synthetic quick start

Run these commands from the repository root:

```bash
margin validate-config --config configs/synthetic.yaml
margin doctor --config configs/synthetic.yaml
margin run --config configs/synthetic.yaml --device cpu
```

The run prints its decision and the locations of its report and manifest. Open
`runs/synthetic/reports/audit_report.md` to inspect the generated evidence and
figures. The expected decision is `SYNTHETIC_ONLY`.

The configuration controls sample generation, model identifiers, analysis groups,
bootstrap settings, decision thresholds, and plot formats. `paths.project_root`
is resolved relative to the YAML file. Other relative input and output paths are
resolved against that project root. Set `paths.run_dir` to a separate directory
for each configuration whose outputs you want to retain.

## Inputs and outputs

For supplied data, the registry accepts either CATH domain-list/FASTA files plus
structures or a canonical directory containing `domains.parquet` and
`residues.parquet`. Benchmark metadata, homology hits, conservation values, assay
labels, and frozen embeddings use typed tables. Supported table readers accept
Parquet, CSV, or TSV where documented by the corresponding loader.

| Table | Required identity and content |
| --- | --- |
| Domains | Unique `domain_id`, canonical sequence, length, structure metadata, CATH groups, analysis role, and training eligibility |
| Residues | `domain_id` and zero-based contiguous `position`, residue identity, backbone coordinates, and environment annotations |
| Benchmarks | Unique `benchmark_id`, sequence, domain/structure identifiers, and CATH groups |
| Homology hits | `domain_id`, `benchmark_id`, sequence identity, query coverage, and target coverage |
| Teacher scores | State/domain/position keys, teacher and structure roles, model metadata, and one `logp_<amino-acid>` column per canonical residue |

The complete column contracts and validation rules are defined in
[registry schemas](src/margin/data_registry/schema.py),
[teacher schemas](src/margin/teachers/schema.py), and
[request exports](src/margin/teachers/requests.py).

Each run contains the following directories:

| Location | Contents |
| --- | --- |
| `registry/` | Domain/residue tables, eligibility decisions, and leakage evidence |
| `state_bank/` | Generated states and per-position policy scores |
| `decoys/` | Matched, permuted, shuffled, and graph-based controls |
| `teacher_cache/` | Adapter requests, canonical scores, and model/cache metadata |
| `audit/` | Metric tables, `decision_criteria.parquet`, and `decision.json` |
| `source_data/` | Plot inputs in CSV and Parquet, named by content |
| `figures/` | `distillability_map` and `audit_overview` in configured formats |
| `reports/` | `audit_report.md` and `run_index.md` |

The run root also contains the original and resolved configuration and
`manifest.json`. Synthetic runs include generated fixture tables in `fixtures/`.
Manifests record runtime context, parameters, artifact paths, and the existing
cache/provenance checks used by the pipeline.

## Command-line interface

Run `margin --help` or `margin <command> --help` for arguments.

| Command | Purpose |
| --- | --- |
| `validate-config` | Validate a YAML configuration and resolve its paths |
| `doctor` | Check configured inputs, tools, and model environments |
| `run` | Execute the configured audit and write tables, figures, and reports |
| `build-candidates` | Build a quality-filtered candidate registry |
| `prepare-registry` | Apply benchmark exclusions and assemble the registry |
| `build-state-bank` | Materialize sequence states and available frozen features |
| `score-teacher` | Run one configured external adapter and normalize its scores |
| `build-homology` | Produce a benchmark-hit table with MMseqs2 |

## Python API

```python
from pathlib import Path

from margin.pipeline import run_audit

result = run_audit(Path("configs/synthetic.yaml"), device="cpu")
print(result.decision.decision)
print(result.report_path)
```

The modules under `margin.data_registry`, `margin.state_sampling`,
`margin.decoys`, `margin.teachers`, and `margin.attribution` expose the individual
steps for workflows that already have intermediate tables.

## Assumptions and optional models

Residue positions are zero-based. Backbone coordinates and distance cutoffs use
angstroms. Score columns follow `ACDEFGHIKLMNPQRSTVWY`; normalized scores use
natural logarithms. CATH-H and CATH-T groups control the configured cross-domain
splits. Bootstrap intervals cluster on the configured unit, which defaults to a
domain. Decision thresholds are configurable analysis settings, and synthetic
runs always return `SYNTHETIC_ONLY`.

Structure preprocessing can use DSSP, and homology searches use MMseqs2. External
model scoring requires a source checkout, user-supplied local checkpoints and
model repositories, and the configured Conda environments. The adapter scripts
live under [scripts/models](scripts/models). Optional ESM2 support is available
through `python -m pip install -e ".[models]"`; its loader uses local model files.
Model integrations have their own dependencies and hardware requirements. The
synthetic tests exercise software contracts without executing those models.
